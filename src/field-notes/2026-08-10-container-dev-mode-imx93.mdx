## The loop this replaces

Picture a computer-vision device. The application is a container: an inference runtime, a pile of Python dependencies, model weights. The image is multi-gigabyte - 7 GB uncompressed is not unusual. It runs on a box in a plant, a yard, or a vehicle, on an immutable OS nobody wants to reflash to try a code change.

So the loop goes: change forty lines of Python, rebuild the image, push the whole thing to a registry, pull the whole thing onto the device, restart, discover the fix was wrong, repeat.

Nothing there is broken, exactly. The cost of one iteration is set by the size of your image instead of the size of your change, and that ratio gets worse every time the model grows. Teams end up batching changes they would rather test one at a time, which is the real tax: not the minutes, the loss of "try it and see".

## What it looks like instead

Name the image you build and the service on the device that runs it, point the CLI at the board, and keep building the way you already do. The CLI watches your engine, pushes only the changed layers into a registry on your host, and notifies the device, which pulls them and restarts the service.

The board stays in the loop the whole time, so what you are watching is your code on the target, not an approximation of it.

## Reproduce it

This assumes you have the board, an SD card and a USB-C cable. You are not building a BSP.

On the host you need a container engine, and QEMU emulation registered for the board's architecture, because you will be building for something other than what you are sitting at. Docker Desktop provides this; on a Linux host it usually comes from a `qemu-user-static` package:

```bash title="On Host"
ls /proc/sys/fs/binfmt_misc/ | grep qemu-aarch64
```

Every step below says which machine it runs on, in its heading and again on each command block. Two machines and an SSH hop between them is exactly the setup where a command run in the wrong place fails in a way that looks like the feature is broken.

### 1. Create the project (on host)

```bash title="On Host"
avocado init --target imx93-frdm imx93-frdm
cd imx93-frdm
```

### 2. Declare the runtime (on host)

Four extensions. The SSH one is the easy miss: `up` delivers the session bootstrap to the device over SSH before the loop exists, and a minimal Avocado image ships no SSH server.

```yaml title="avocado.yaml"
distro:
  release: 2026
  channel: edge

runtimes:
  dev:
    target: imx93-frdm
    extensions:
      - docker # the container engine
      - container-agent-dev # the device agent
      - sshd-dev # up delivers the session bootstrap over SSH
      - my-app # your app: its image and the unit that runs it

    container_dev:
      images:
        - ref: my-app:dev
          service: my-app

extensions:
  my-app:
    # Both types are required. The unit ships in the sysext under /usr/lib;
    # enable_services writes its enablement symlink under /etc, which is
    # confext territory. With only one, the unit is present but never starts.
    types: [sysext, confext]
    version: 1.0.0
    overlay: overlay

    enable_services:
      - my-app.service

    # Seeds the image into the /var partition at build time, so the very first
    # boot has something to run before any sync has happened.
    docker_images:
      - image: my-app
        tag: dev
```

`service` names the unit on the device that owns the container, and it is not decoration. With it, a sync restarts that unit, so `ExecStart` re-runs `docker run` and re-resolves the tag. Without it the agent falls back to an engine `restart`, which re-executes the existing container object - bound to the image ID it was created with - and the device keeps running the old code while every layer reports success.

The unit goes at `overlay/usr/lib/systemd/system/my-app.service` - that exact path, because it is where `enable_services` looks for it. A unit placed anywhere else produces an extension that builds, merges, presents the unit, and leaves it disabled forever.

```ini title="overlay/usr/lib/systemd/system/my-app.service"
[Unit]
Requires=docker.service
After=docker.service

[Service]
ExecStartPre=-/usr/bin/docker rm -f my-app
ExecStart=/usr/bin/docker run --rm --name my-app -p 8080:8080 my-app:dev
ExecStop=/usr/bin/docker stop my-app
Restart=always

[Install]
WantedBy=multi-user.target
```

`Restart=always`, not `on-failure`: with `--rm` and a default `Type=simple`, a container that exits cleanly leaves the unit inactive with nothing to bring it back.

### 3. Build and provision (on host)

```bash title="On Host"
avocado install -f
avocado build
avocado provision -r dev --profile sd
```

This is the long part, and the only long part. `install` and `build` pull and assemble the runtime, which on a cold cache is tens of minutes; `provision` writes the card. Everything after this step is seconds, so if you are timing the loop, start the clock here.

The CLI prompts you to pick the block device. It overwrites the one you choose.

### 4. Boot it (on the board)

The board's debug console is on its onboard USB-C port and enumerates as two CDC-ACM devices; the Linux console is the first.

```bash title="On Host"
ls /dev/serial/by-id/
tio -b 115200 /dev/serial/by-id/usb-1a86_USB_Dual_Serial_<serial>-if00
```

Insert the SD card, connect USB-C, apply power. Log in as `root` with an empty password, and read the address the loop will use:

```bash title="On the console"
ip -4 addr show
```

Your container is already running - `docker_images` seeded the image and `enable_services` enabled the unit, so the board came up serving it:

```bash title="On the console"
systemctl is-active my-app.service
docker ps
```

### 5. Confirm SSH before starting the loop (host to board)

```bash title="On Host"
ssh root@<device-ip>
```

If this fails, `up` cannot bootstrap the device. Fix it here rather than debugging it as a container problem later.

### 6. Start the session (on host)

```bash title="On Host"
export AVOCADO_CONTAINER_DEV_DEVICE=root@<device-ip>
avocado container dev up
```

`up` runs in the foreground and stays there for as long as you want the loop: it is the registry and the file watcher, so closing it ends the session. Give it a terminal of its own.

It takes a couple of seconds and ends on a line naming the bulk listener it opened, plus `device <ip> bootstrapped`. That listener line is the readiness signal - until it appears there is nothing for a sync to talk to. On the device, the agent's path unit starts its service the moment the bootstrap file lands, so you do not start anything on the board yourself.

### 7. Change the app and watch it land (host, then the board)

Edit your application, then rebuild for the board's architecture:

```bash title="On Host"
docker build --platform linux/arm64 -t my-app:dev .
avocado container dev sync
```

Two things differ from a same-architecture setup, and both bite immediately. An x86-64 host builds an x86-64 image the board cannot execute - the device-side pull refuses it rather than shipping it, so the failure lands at sync time rather than at runtime. `--platform` fixes that and costs a second problem: it routes the build through buildx, which is BuildKit, so the watcher may see no tag event at all. Pairing the cross-build with an explicit `sync` sidesteps both.

The size difference between the first sync and this one is the whole point, and it is worth watching rather than taking on faith. The registry keeps its blobs under `~/.avocado/container-dev` on the host, and it writes each blob exactly once - a layer already there is never re-sent. So the directory's growth across a sync is what actually crossed to the device:

```bash title="On Host"
du -sh ~/.avocado/container-dev
```

Check it before and after. On my run the first delivery moved the whole image and every later one moved only the rebuilt top layer - megabytes against kilobytes, on an image small enough to be honest about. Scale that ratio to a multi-gigabyte inference image and it is the entire argument for the loop.

Your change is now serving from the board:

```bash title="On Host"
curl http://<device-ip>:8080/
```

## How you know it actually worked

The tell is the container's age, not the page contents:

```text
CONTAINER ID   IMAGE        STATUS          NAMES
37bb47e38cc4   my-app:dev   Up 30 seconds   my-app
```

Seconds old means the unit genuinely re-ran and re-resolved the tag. Under the engine-`restart` fallback the container would keep its original age and serve the old image while every layer reported success - which is the failure mode worth knowing about, because nothing in the output says anything is wrong.

A single `curl` after the fact is a weaker check than it looks: it tells you what is serving now, not that anything changed. Have the app print a version string on a timer, and watch the log from the host across the rebuild instead of sampling it once:

```bash title="On Host"
ssh root@<device-ip> 'journalctl -u my-app.service -f -o cat'
```

Leave that running, rebuild in the other terminal, and you see the old version repeating, then the new one, in one stream. That distinguishes "it is serving the new code" from "it was already serving this and nothing happened", which a one-shot request cannot. Make the version obvious in the line - it arrives as one line among several identical ones, and it is easy to scroll straight past the moment you were waiting for.

One thing not to check: the image ID reported on the device against the one on your host. They legitimately differ. The device's containerd image store reports the manifest digest and a local build reports the config digest, so comparing them sends you chasing a mismatch that is expected. Compare your own version string instead.

## If you run it more than once

A second pass is not a clean repeat of the first, and three things caught me going round again.

`up` refuses to start while a previous session is still alive, and the previous session outlives the terminal you think you closed it in. Ask the CLI rather than hunting for the process:

```bash title="On Host"
avocado container dev status
avocado container dev down
```

`status` reports whether the registry and watcher are running and when the last sync happened. `down` signals the session to stop and tears down every listener, including the authenticated write port, and it clears the session state even when the process behind it is already gone - so it is also the way out of a half-dead session, not only a tidy one.

The transfer figures do not repeat either. Blobs already in `~/.avocado/container-dev` are never re-sent, so a second run reports a first delivery of almost nothing - which reads as a fantastic result and is really just the earlier run's leftovers. Clear that directory before measuring anything. `avocado container dev prune` is the reclaim command, but it is not the one you want here: it sweeps only blobs no currently-tagged manifest references, so the layers you are about to re-send are exactly the ones it keeps.

On the board, restarting the agent repeatedly inside a few minutes trips systemd's start rate limit and the next start is refused outright, with a message about starting too often rather than anything about the loop. Clear the counter and start again:

```bash title="On the console"
systemctl reset-failed container-agent-dev.service
```

## What surprised me

The failures on this path are quiet ones. An extension whose unit sits in the wrong directory builds, merges, presents the unit, and reports success - and `systemctl is-enabled` answers `disabled` on every boot with no journal entry explaining why. A wrong-architecture image fails at sync rather than at runtime. A missing SSH server presents as a container problem. None of them announce themselves, which is why the steps above call out the three places where a quiet failure is waiting rather than leaving them to be discovered.

**TL;DR.** On the same Orin Nano 8GB, Avocado OS sets up in 6 minutes 56 seconds instead of about 30 minutes. It uses 93% less disk and 49% less idle RAM than JetPack 7.2.1, and draws the same power.

**Ubuntu + JetPack 7.2.1** (stock desktop)

- Setup: about 30 minutes, 12 manual steps
- Disk: 35,027 MiB with `nvidia-jetpack` installed
- RAM used: 866 MiB at idle, 1255 MiB with the model running
- Production readiness: desktop, `dockerd` running, 365 pending updates, no SSH host keys

**Avocado OS**

- Setup: 6 minutes 56 seconds, 4 commands
- Disk: 2,545 MiB with TensorRT, the model and the engine
- RAM used: 444 MiB at idle, 877 MiB with the model running
- Production readiness: immutable root filesystem, built for OTA updates through Peridio (not measured here)

Throughput is 466 to 471 queries per second on JetPack and 491.6 on Avocado OS. Power is 16.5 W against 16.3 W with the model running. Every figure is one install and one run on 2026-11-09, with a ResNet-50 FP16 engine in the 25 W power mode.

## What this is

Avocado OS is a Yocto-based Linux distribution. It ships an immutable root filesystem with extensions layered on top. Peridio builds its fleet platform around it.

This note compares it with JetPack 7.2.1 on one Orin Nano 8GB: setup time, disk use, production readiness, RAM, power and throughput.

## How I measured it

The board is a Jetson Orin Nano 8GB devkit. I used two images:

- **JetPack 7.2.1**, as a typical user runs it. I installed NVIDIA's `jetsoninstaller-r39.2.1-2026-08-07-18-30-47-arm64.iso` (5,035,601,920 bytes) to the NVMe. The result is Ubuntu 24.04 with the GNOME desktop, kernel 6.8.12-1021-tegra and default services. The stock install has no CUDA, TensorRT or `trtexec`. `apt-get install nvidia-jetpack` adds them (TensorRT 10.16.2.10).
- **Avocado OS**, from the `jetson-orin-nano-power` reference. It merges the `avocado-bsp-jetson-orin-nano`, `avocado-ext-dev`, `avocado-ext-sshd-dev`, `avocado-ext-bringup` and `avocado-ext-trt` extensions on linux-yocto 6.18.52. The board support extension comes from bsp-jetson-orin-nano PR #6. It sets the 25 W power mode and the CPU and GPU governors at boot. I built it as a local path extension because the feed version does not have it yet. I built the measured image with Avocado CLI 1.1.0-dev. I then built, flashed and booted the same project with the released 1.0.0. All five extensions merged and the board came up in the 25 W mode.

Both images run TensorRT from native packages, not a container. `trtexec` is in `/usr/src/tensorrt/bin`. I did not measure a container path. [NVIDIA's TensorRT container page](https://docs.nvidia.com/deeplearning/tensorrt/latest/installing-tensorrt/install-container.html) names Jetson AGX Orin and Jetson Thor for Jetson, not the Orin Nano. It lists a multi-GB download and extra container overhead as limits of that path.

The test uses no camera. `trtexec` feeds the engine its own inputs, so the numbers cover the engine and the memory around it, not a camera pipeline.

RAM used is `MemTotal` minus `MemAvailable` from `/proc/meminfo`. On JetPack it equals the used column of `free -m`. Both images ran the same protocol. Cold boot, then wait 240 seconds. Take three idle readings 5 seconds apart. Run `trtexec` for 60 seconds. Take three more idle readings. I sampled `MemAvailable` every 2 seconds throughout.

The model is `resnet50-v1-12.onnx` from the ONNX model zoo (102,576,593 bytes, sha256 checked on both boards). Each board built its own FP16 engine with `trtexec --onnx=... --fp16`. It then ran the engine with `--loadEngine=... --duration=60 --warmUp=1000`. The build took 73 seconds on JetPack (51,641,260-byte engine) and 80 seconds on Avocado OS (51,590,116 bytes).

## Ubuntu + JetPack 7.2.1

### Getting started

JetPack comes as a 5.0 GB ISO. A person writes the card, boots the installer from the UEFI menu, picks the target and works through the first-boot setup. The result is a general-purpose Ubuntu image with desktop and server services that an embedded product must strip out later.

I counted 12 manual steps. Write the ISO. Make two GRUB menu selections. Answer seven first-boot dialogs (license, language, location, keyboard, network, time zone, user account). Enable `sshd`. Install `nvidia-jetpack`.

Problems that cost time on an embedded device:

- **The installer fails on a board that ran Avocado OS before.** On 2026-11-06 the stock installer stopped at Step 9 of 13 on four runs, with `An error occurred. Press enter to start a shell`. Avocado OS flashing leaves its own firmware in the QSPI flash. NVIDIA's bootloader package reads the board name from that firmware (`3767--0005--1--avocado-jetson-orin-nano-`) and rejects it as an unknown board. I flashed NVIDIA's stock QSPI firmware back (`flash.sh jetson-orin-nano-devkit-super-qspi internal`, 516 seconds, recovery mode). The same installer then passed Step 9 and booted on its own on 2026-11-09. A factory board has stock firmware and does not hit this. Recovery mode is only for the flash, not for the installer.
- `Install on NVMe` runs unattended from a fixed configuration. It asks nothing about keyboard, user, storage layout or network, so you cannot fix a problem before it fails. The other targets open the interactive installer.
- `Install on microSD` failed on this bench. The installer stopped with `preseed: force-bootdisk=mmcblk0 is not a valid storage device. Starting interactive installer.` because `lsblk` listed no `mmcblk0`. Booting the installer from the card failed with `Unable to find a medium`. The card sat behind an SDWire3 SD-card mux, which UEFI listed as `UEFI SanDisk SN64G SD Device`. I did not find out whether the mux or the installer kernel hides it, so I installed to the NVMe.
- The stock image's `sshd` has no host keys. I enabled it by hand.
- 365 package updates were pending after the install.
- At idle the largest resident processes were `gnome-shell` (226 MB), `nvargus-daemon` (135 MB), `mutter-x11-frames` (122 MB), `Xorg` (84 MB) and `dockerd` (79 MB).

### Timing

These times come from the 2026-11-09 install, except where noted:

- **ISO download:** not timed. It depends on your bandwidth.
- **Write the ISO to the card:** 79.7 seconds with `dd` at 63.2 MB/s, then a byte-for-byte compare (2026-11-06).
- **Installer, from `Install on NVMe` to its last step:** 12 minutes 56 seconds (18:22:16 to 18:35:12). Step 5 of 13, `Installing required packages`, takes the longest. The installed system booted 2 minutes later.
- **First-boot dialogs and `sshd`:** not logged. They took a few minutes by hand.
- **`apt-get install nvidia-jetpack`:** 6 minutes 10 seconds. It downloaded 9,468 MB in 2 minutes 15 seconds (70.1 MB/s) and added 26,166 MiB (8,861 to 35,027 MiB).
- **Total:** about 30 minutes from a written card to a configured board.

### Takeaways

- **Numbers:** about 30 minutes to a configured board and 35,027 MiB of disk. RAM: 866 MiB at idle, a 1255 MiB peak with the model running, 6230 MiB left at the low point.
- **Experience:** 12 manual steps on every board. The installer needs stock firmware and failed on four runs without it. Only the NVMe target runs unattended.
- **Production readiness:** a general-purpose Ubuntu desktop with `dockerd` running, 365 pending updates and no SSH host keys until someone enables `sshd`. A hundred boards mean a hundred manual installs.
- **Against Avocado OS:** JetPack takes about 4.3 times as long to set up. It uses about twice the RAM at idle, about 43% more at the peak, and about 14 times the disk. It leaves about 400 MiB less RAM available at idle.

## Avocado OS

### Getting started

Four commands install Avocado OS from the project. I recorded them in one pass from a clean project directory on 2026-11-06 (host time, from the recording's marks):

- **`avocado install -f`:** 69 seconds, in a directory with no earlier install state and the SDK image already on the host.
- **`avocado build`:** 7 seconds.
- **`avocado provision -r power --profile tegraflash-nvme`:** 4 minutes 49 seconds, including the var image build and the flash. It asks for no confirmation.
- **Boot:** the board booted the new image on its own, 38 seconds after the flash ended (21:30:56). It reached the automatic root login on the serial console at 21:31:34. There was no power cycle and no step at the board.

All four extensions merged on first boot (`Total: 4 extension(s), 4 merged`), on Avocado OS 2026.73 with kernel 6.18.52. The image takes OTA updates, and Peridio manages it as a fleet. You provision the board once and update it in place.

TensorRT is one more extension. Build it with `-r trt` instead of `-r power`. The libraries come with the image, so nothing installs on the board. On the board I fetched the model (2 seconds) and built the engine (80 seconds).

### Timing

- **Total:** 6 minutes 56 seconds from the first `avocado install` to the login. Setting up recovery mode is not counted.
- **SDK image download:** not counted, because it depends on bandwidth. The SDK image is 140 MB. The project's SDK volume grew to about 5.5 GB after the install.

### Takeaways

- **Numbers:** 6 minutes 56 seconds to a logged-in board and 2,545 MiB of disk with TensorRT. RAM: 444 MiB at idle, an 877 MiB peak with the model running, 6587 MiB left at the low point.
- **Experience:** four commands, no step at the board. The board boots the new image by itself.
- **Production readiness:** an immutable root filesystem with extensions on top, OTA updates, and fleet management through Peridio. The reference carries three development extensions, including a root serial console and root SSH. Remove them before shipping.
- **Against JetPack:** Avocado OS takes about 77% less time to set up. It uses about 49% less RAM at idle, about 30% less at the peak, and about 93% less disk. It leaves about 400 MiB (about 6%) more RAM available at idle.

### What the headroom buys

The ResNet-50 run cost about 430 MiB of available RAM on Avocado OS. The 400 MiB idle gap is close to one more copy of this workload. On an 8 GB module, that room holds:

- a second model resident at the same time, such as a detector and a classifier, instead of swapping them
- more concurrent camera streams, each with its own decode and preprocessing buffers
- a larger batch size or a higher input resolution on the same model
- a larger model, such as a bigger backbone or a small language model, in the memory the desktop would use
- the rest of the product next to the model: the camera pipeline, an application server and the device agent
- headroom for an OTA update, such as staging a new image or running the old and new application side by side during a rollout
- a safety margin against out-of-memory kills when an allocation spikes, on a device in the field with no one to restart it
- a cheaper module, if a workload that fits in 8 GB on JetPack also fits in less on Avocado OS

I did not test a smaller module.

### Power and throughput, on the same board

With the power profile, Avocado OS matches JetPack on power and runs the engine about 5% faster. The module's power monitor (INA3221, VDD_IN rail) read this over the idle windows and the 60-second run:

| State                    | JetPack 7.2.1 | Avocado OS |
| ------------------------ | ------------- | ---------- |
| Idle, mean               | 4.93 W        | 4.72 W     |
| Model running, mean      | 16.49 W       | 16.28 W    |
| Throughput (qps)         | 466 to 471    | 491.6      |
| Queries per second per W | about 28.5    | about 30.2 |

That is module power only. It excludes the carrier, fan and peripherals. JetPack figures come from `tegrastats` and Avocado OS figures from the monitor. An earlier headless JetPack boot read 4.84 W at idle.

The power profile sets the 25 W power mode and the `schedutil` CPU and `simple_ondemand` GPU governors at boot, through the board support package. Without it, the Jetson kernels boot on the `performance` governors with the GPU parked at 918 MHz. The same image then idled at 6.53 W, drew 19.8 W with the model running and reached 601.6 queries per second. Nothing scales the clocks down. A project built from the feed alone behaves that way today, and it is not comparable with JetPack. The profile costs about 50 MiB of RAM. The reference project ships `verify-power.sh`, which reads the monitor so you can check the number on your own hardware.

**What to take from it:** set the power profile. With it, Avocado OS matches JetPack on power, runs slightly faster and leaves about 400 MiB more RAM.

With the governors active, the kernel logged `devfreq 17000000.gpu: Couldn't update frequency transition information.` repeatedly while the model built and ran. I did not find the cause. The run was otherwise normal.

The governors unit is in review (bsp-jetson-orin-nano PR #6). The BSP on the feed, 0.2.1, lacks it. On a board flashed from the feed, `avocado-idle-governors.service` does not exist, and `nvpmodel.service` and `nvpower.service` are `disabled`. `nvpmodel -q` prints `power mode is not set!`, the GPU devfreq node is missing and the CPU governor is `performance`. Until that change ships, a project built from the feed does not reach these figures. I built the Avocado OS image in this note with the BSP pointed at the PR branch.

## Reproduce it

You need:

- a Linux host with Docker and the Avocado CLI
- a Jetson Orin Nano 8GB devkit
- a USB-C cable
- a jumper wire for the FC_REC pin
- a USB serial adapter for the debug console

The project's `getting_started.md` covers recovery mode.

### Avocado OS side

```bash
avocado init --reference jetson-orin-nano-power jetson-orin-nano-power
cd jetson-orin-nano-power
avocado install -f
avocado build
avocado provision -r power --profile tegraflash-nvme
```

Use `--profile tegraflash-sd` for an SD card. Both profiles overwrite the target and rewrite the QSPI firmware and the UEFI variables.

Until the governors change ships, point the `avocado-bsp-jetson-orin-nano` extension at a checkout of the PR branch (`source: {type: path, path: ../bsp}` in `avocado.yaml`).

After the flash, remove the jumper. A power cycle with the jumper fitted returns the board to recovery mode. Connect to the debug console (115200 baud) and install your key in `/var/lib/ssh/authorized_keys`. Then read memory and power from the host:

```bash
ssh root@<device-ip> "free -m | awk 'NR==2{print \$3 \" MiB used, \" \$7 \" MiB available\"}'"
ssh root@<device-ip> sh -s < verify-power.sh
```

### JetPack side

1. If you ran Avocado OS on the board before, flash NVIDIA's stock QSPI firmware first, with the board in recovery mode (about 9 minutes). A factory board does not need this.
2. Write the `jetsoninstaller-r39.2.1-...-arm64.iso` to a USB stick. Boot it from the UEFI Boot Manager (F11 on the serial console). Recovery mode is not needed.
3. If the installer asks to update the firmware, answer `Y`. Choose `Install Jetson ISO`, then `Install on NVMe`.
4. Finish NVIDIA's first-boot setup on the USB device-mode serial port (`/dev/ttyACM0` on the host).
5. Enable SSH, then add the JetPack packages:

   ```bash
   sudo ssh-keygen -A && sudo systemctl enable --now ssh
   sudo apt-get install nvidia-jetpack
   ```

6. Reboot and wait 4 minutes for first-boot work to settle. Read idle memory three times, 5 seconds apart:

   ```bash
   free -m | awk 'NR==2{print $3 " MiB used, " $7 " MiB available"}'
   ```

   Power comes from `tegrastats`.

### With a model loaded

The model is `resnet50-v1-12.onnx` from the ONNX model zoo (102,576,593 bytes, sha256 `3f03fdef724b22947eed826f1eef1dc5c34151bb4c37d634f1db89dfa2dd1526`).

On Avocado OS, the reference's `trt` runtime adds one extension, `avocado-ext-trt`. Its `packages:` list names `tensorrt-trtexec-prebuilt`, `tensorrt-plugins-prebuilt`, `libnvinfer10`, `libnvinfer-builder-resource-ptx`, `cudnn` and `libcublas`. All come from the feed at the JetPack 7.2.1 versions (TensorRT 10.16.2.10, cuDNN 9.20.0.46, cuBLAS 13.4.1.3). Build and provision it with `-r trt` in place of `-r power`. Without `tensorrt-plugins-prebuilt`, `trtexec` stops with `Unable to open library: libnvinfer_plugin.so.10`. On the board:

```bash
mkdir -p /var/trt && cd /var/trt
curl -ksSL -o resnet50-v1-12.onnx 'https://media.githubusercontent.com/media/onnx/models/main/validated/vision/classification/resnet/model/resnet50-v1-12.onnx'
sha256sum resnet50-v1-12.onnx
/usr/src/tensorrt/bin/trtexec --onnx=resnet50-v1-12.onnx --saveEngine=resnet50.plan --fp16
sync
```

The image has no CA bundle, so the command uses `curl -k`. The checksum establishes the file. Run `sync` before you power-cycle. On one run, an engine written just before a power cycle came back as a 0-byte file, and `trtexec` failed with `read 0 out of 32 bytes`. I did not find the cause.

Then cold-boot the board and wait 240 seconds. Read memory three times, 5 seconds apart. Run `trtexec --loadEngine=resnet50.plan --duration=60 --warmUp=1000` while you sample `MemAvailable` every 2 seconds. Read memory three more times. JetPack uses the same flags with `/usr/src/tensorrt/bin/trtexec`. The Avocado OS root filesystem allows no writes, so the model and engine live under `/var`.

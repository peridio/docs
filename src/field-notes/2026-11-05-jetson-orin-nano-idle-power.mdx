**TL;DR.** A minimal Avocado OS runtime idled a Jetson Orin Nano 0.72 W above where it should, because nothing set a power mode or scaled the CPU and GPU frequency. With the 25 W mode and the `schedutil` and `simple_ondemand` governors applied at boot, the module idles at 4.75 W, against 4.84 W for JetPack 7.2.1 on the same board. That is one reading from a different tool, so the claim is "within noise".

{/* truncate */}

## What this is

Avocado OS is a Yocto-based embedded Linux distribution that ships as an immutable root filesystem plus extensions layered on top of it. Peridio builds the device fleet platform around it. A customer with an Orin Nano product on a battery asked whether Avocado idles as low as JetPack, NVIDIA's stock Ubuntu-based image, so I measured it.

All numbers here are module power: the INA3221 monitor on the module's VDD_IN rail, read through `hwmon` once a second. The carrier, fan and peripherals are excluded, and a battery budget is set against the whole device.

## What was wrong

On the measured devkit, a runtime without the governors idled at 5.47 W against 4.75 W with them (one run each). The Jetson kernels boot with the `performance` CPU governor, and the GPU's devfreq governor starts on `performance` too, so the GPU sits at 918 MHz while nothing runs. JetPack runs a service that sets a power mode and scales both.

A minimal Avocado runtime had neither. The board support extension shipped `nvpower` and `nvpmodel`, but package presets are not applied on an immutable image, so the units stayed disabled, no power mode was set, and the GPU devfreq node did not exist until they ran.

## What I changed

The fix is one unit in the board support extension's confext (`avocado-bsp-jetson-orin-nano`), ordered after `nvpmodel`, which sets the 25 W mode and creates the GPU node:

```ini
[Unit]
Description=Scale CPU and GPU frequency with load
Wants=nvpmodel.service
After=nvpmodel.service nvpower.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/bin/sh -c 'g=/sys/class/devfreq/17000000.gpu/governor; [ -e $$g ] && echo simple_ondemand > $$g; for c in /sys/devices/system/cpu/cpu[0-9]*/cpufreq/scaling_governor; do echo schedutil > $$c; done'

[Install]
WantedBy=multi-user.target
```

Two details worth copying. `$$` reaches the shell as a literal `$`; a single `$` is expanded by systemd first and the loop silently writes nowhere. The GPU write is guarded by a test for the node, so a feed without `nvpmodel` skips it instead of waiting or failing, and the CPU governor is still set.

[ENGINEER: confirm the published `avocado-bsp-jetson-orin-nano` package carries this unit; it was in review, not merged, when I measured it from a local build.]

The reference project assembles a runtime from four feed packages, with no compile step: the board support extension, `avocado-ext-dev` (grows `/var` on first boot), `avocado-ext-sshd-dev` and `avocado-ext-bringup` (a way in on a board with nothing provisioned). Its `verify-power.sh` reads the monitor so you can check the number on your own hardware.

## Result

<PullQuote>The module idles at **4.75 W** from a cold boot, within noise of JetPack 7.2.1's **4.84 W**. Forcing the performance governors costs about **0.7 W**.</PullQuote>

- **The governors are worth about 0.7 W at idle.** With the GPU and CPUs forced to `performance` the board idled at 5.47 W (60 s window). With `simple_ondemand` and `schedutil` it idled at 4.747 W in the 89 s cold-boot window and 4.753 W in a 60 s window, on the same runtime, one run each. Almost all of the difference is the GPU.
- **A warm reboot reproduces it.** After `reboot` and a 240 s settle the script read 4717 mW (n=89), against 4747 mW from the cold boot.
- **It matches JetPack at idle.** JetPack 7.2.1 idled at 4.84 W on the same board, read with `tegrastats`. The JetPack side is one boot, one tool and one day, and its conditions (headless or desktop, power mode) are not recorded, so a lead of 0.09 W could disappear.
- **Memory is the other number.** On a bare Avocado image idle used memory was 363 to 368 MiB on both the L4T 6.8 and linux-yocto 6.18 kernels. Headless JetPack was 563 to 566 MiB on one boot. The reference runtime, with four extensions and an SSH session, used 444 MiB.

### Governor choice

At idle, `ondemand` read 4.76 W against 4.85 W for `schedutil` in the same session (60 s windows, run in sequence, so the difference is inside the noise). `schedutil` is chosen for load-following behavior, not an idle gain. A kernel config default (`CONFIG_CPU_FREQ_DEFAULT_GOV_SCHEDUTIL`) was rejected because it recovers only 0.04 to 0.15 W, since the CPUs are the small part of the gap.

On the GPU, `nvhost_podgov` read 4.81 W, `tegra_wmark` 4.77 W and `simple_ondemand` 4.85 W at idle. All four scaling governors idle within 0.1 W, and `performance` costs 0.7 W. I did not measure them under GPU load: the runtime ships no CUDA or TensorRT workload, so that comparison needs one, such as the `jetson-trt` reference.

Under a six-process `sha256sum` load (768 MiB per process) in the 25 W mode the two CPU governors matched: 14 s and about 6.6 W each. Each figure is one run with 1 s timing.

## Issues Encountered

**The 15 W mode is not a battery mode for CPU-only work.** This reference uses the 25 W mode because it is JetPack's default. On an earlier bitbake-built image running a ResNet-50 FP16 TensorRT engine, the 15 W mode (mode 0) gave 11.4 W and 325 queries per second against 17.6 W and 483 at 25 W. On this runtime a CPU-only load does not follow that pattern: with six `sha256sum` processes the 15 W mode finished in 12 s at 7.05 W and the 25 W mode in 14 s at 6.64 W, repeated twice with the same result. `nvpmodel.conf` caps the CPU at 1497.6 MHz and the GPU at 612 MHz in mode 0, and at 1344 MHz and 918 MHz in mode 1, so a GPU-bound load is where the 15 W mode would be expected to cost throughput. I did not repeat the TensorRT comparison on this runtime.

**The base runtime can hang at boot.** On some boots the root filesystem blocks at `Early TPM SRK Setup`, with no timeout, waiting for a TPM device the firmware never creates (the fTPM is not enabled). Masking `systemd-tpm2-setup-early.service` on the kernel command line avoided it in every boot I tried. The reference does not set the mask: it would hide a hang whose cause is unknown, and it spends part of the boot image's 511-byte command-line budget.

**`avocado provision` could not flash from its container on the host I developed on.** It failed at the first step with `could not retrieve chip ID`. I flashed from the host with `avocado-flash` from an exported stone directory instead. The var image is rebuilt only by running provision, so `avocado build` alone leaves a board with stale extensions. [ENGINEER: confirm provision flashes a Jetson from the container on a clean host.]

**`/boot/efi` fails to mount on an SD card, and boot continues.** The journal shows `Failed to create mount point '/boot/efi', ignoring: Read-only file system`, then `mount point does not exist`, because the erofs rootfs has no `/boot/efi` directory. The unit is `WantedBy=local-fs.target`, not required, which is why boot continues. I found no other unit naming `/boot/efi` under `/usr/lib/systemd/system` and `/etc/systemd/system`; I did not check what else reads that path.

**The debug extensions give root to anyone with the console.** `avocado-ext-sshd-dev` (root SSH login), `avocado-ext-dev` (development tools) and `avocado-ext-bringup` (a root serial console) are development extensions. Remove all three before shipping. The root account in the base rootfs is locked and `/root` and `/var` are not writable before first boot, so a key cannot be baked in; a serial autologin is the way in.

**One feed, one board.** Only the 2026 `next` feed and the Orin Nano 8GB devkit were checked. [ENGINEER: confirm `avocado-ext-bringup` is published to the feed before this note ships; it was not when the reference project's first CI run tried to install it.]

## Reproduce it

You need a Linux host with Docker and the Avocado CLI, a Jetson Orin Nano 8GB devkit, a USB-C cable, a jumper wire for the FC_REC pin, and a USB serial adapter for the debug console. The project's `getting_started.md` has the full flow, including recovery mode. [ENGINEER: run this flow once from a clean checkout of the published reference; I ran the commands from a local project.]

```bash
avocado init --reference jetson-orin-nano-power jetson-orin-nano-power
cd jetson-orin-nano-power
avocado install -f
avocado build
avocado provision -r power --profile tegraflash-sd
```

Use `--profile tegraflash-nvme` for an NVMe drive. Both erase the target entirely and rewrite the QSPI firmware and the UEFI variables.

Get onto the board through the debug console (115200 baud), which `avocado-ext-bringup` logs in as root. Install your key and read the address:

```bash
mkdir -p /var/lib/ssh
echo 'ssh-ed25519 AAAA... you@host' >> /var/lib/ssh/authorized_keys
ip -brief address
```

Then check the state and read the number from the host:

```bash
ssh root@<device-ip> avocadoctl status
ssh root@<device-ip> systemctl is-active nvpower.service nvpmodel.service avocado-idle-governors.service
ssh root@<device-ip> sh -s < verify-power.sh
```

Expected: four extensions merged, three lines of `active`, then a power line near `idle VDD_IN: mean=4747 mW` with `gpu: simple_ondemand at 306000000 Hz` and `cpu0: schedutil`. The script waits for 240 s of uptime, then samples for 90 s; `SETTLE` and `WINDOW` override both. This is one board, and the board-to-board spread is not known.

To see the gap yourself, force the performance governors and sample again, then reboot to restore the scaling ones:

```bash
ssh root@<device-ip> 'echo performance > /sys/class/devfreq/17000000.gpu/governor; for c in /sys/devices/system/cpu/cpu[0-9]*/cpufreq/scaling_governor; do echo performance > $c; done'
ssh root@<device-ip> SETTLE=0 WINDOW=60 sh -s < verify-power.sh
```

Expect about 5.45 W, with the GPU at 918 MHz.

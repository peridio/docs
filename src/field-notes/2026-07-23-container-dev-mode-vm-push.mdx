**TL;DR** - If you ship a containerized app to an embedded device, your inner loop is probably "rebuild the image, move gigabytes, restart, find out". Container Dev Mode makes it "run `docker build`, and only the changed layer moves". I proved the whole path in a disposable QEMU lab before touching hardware: a one-line change synced **only the changed layer**, and the lab caught two real bugs first - the write registry was serving plain HTTP where the guest required HTTPS, and a 2 MiB body limit was rejecting every real image layer.

## The loop this replaces

Picture a setup we see constantly on computer-vision devices. The application is a container: an inference runtime, a pile of Python dependencies, model weights. The image is multi-gigabyte - 7 GB uncompressed is not unusual, roughly half that on the wire. It runs on a Jetson-class box sitting in a plant, a yard, or a vehicle, on an immutable OS nobody wants to reflash to try a code change.

So the loop goes: change forty lines of Python, rebuild the image, push the whole thing to a registry, pull the whole thing onto the device, restart, discover the fix was wrong, repeat.

Nothing there is broken, exactly. It is that the cost of one iteration is set by the size of your image instead of the size of your change, and that ratio gets worse every time the model grows. Teams end up batching changes they would rather test one at a time, which is the real tax: not the minutes, the loss of "try it and see."

Avocado OS already had an answer for the other half of this problem. [Hardware in the loop](/developer-reference/hardware-in-the-loop) NFS-mounts an extension into a running device so a change shows up in seconds. Container Dev Mode is that same bargain for the container half.

## What the loop looks like now

Name the image you build and the service that consumes it:

```yaml title="avocado.yaml"
runtimes:
  dev:
    container_dev:
      images:
        - ref: my-app:dev
          service: app
```

Point the CLI at the device and start a session:

```bash title="On Host"
export AVOCADO_CONTAINER_DEV_DEVICE=root@192.168.1.50
avocado container dev up
```

Then keep building exactly the way you already do:

```bash title="On Host"
docker build -t my-app:dev .
```

The device stays in the loop the whole time, so what you are watching is your code on the target, not an approximation of it. A QEMU target and a board on your desk are the same thing here: both are just an SSH-reachable device.

```text
// highlight-orange-start
                      edit your app                     <-- you
                            │
                            ▼
              docker build -t my-app:dev .              <-- your normal build
                            │
                            ▼
// highlight-orange-end
// highlight-green-start
                  avocado container dev                 <-- started by dev up
               ┌─────────────────────────┐
               │ watcher   sees the tag  │
               │ registry  keeps layers  │
               │ control   notifies      │
               └─────────────────────────┘
                            │
                            │   only the changed layer
                            ▼
// highlight-green-end
// highlight-blue-start
              the device (QEMU or a board)              <-- hardware in the loop
               ┌─────────────────────────┐
               │ container-agent-dev     │  pulls over the pinned CA
               │ engine  my-app:dev      │  changed layer applied
               │ systemd restart app     │  service back up
               └─────────────────────────┘
                            │
                            ▼
              watch it run on real hardware
// highlight-blue-end
                            │
                            └────▶ edit again, seconds, no reflash
```

That is the loop. There is no wrapper command and no separate push step. The CLI watches your engine for the tag event, pushes the changed layers into an embedded registry on your host, and notifies the device over a control WebSocket; the device pulls and restarts the service. Setup, the full command set, and the trust model are in the [Container dev mode guide](/developer-reference/container-dev-mode).

## What actually moves

Delta-pull is the entire point, so it is the thing worth measuring rather than asserting. With a 512 KiB shared base layer and a small top layer, the first sync moves the whole image. After a one-line change to the top layer, the device pulls only that layer: the config and base blobs are byte-identical by digest and already local.

Scale that to a real inference image and it is the difference between moving gigabytes and moving a few hundred kilobytes for the same edit.

## Proving it before any hardware

The hardest path here is not the one most people hit first. On native Linux the host engine pushes to a loopback registry and Docker's built-in `127.0.0.0/8` exemption means zero certificate config. But when the engine runs inside a VM - the macOS setup - the push has to cross from guest to host over a routable, authenticated HTTPS endpoint whose per-project CA is delivered at session start and never baked into an image. I wanted that proven in software before a board was in the loop.

QEMU user-mode networking hands a guest a fixed route to the host at `10.0.2.2`, the same alias the real helper VM uses, so a plain Debian VM with docker and ssh is a faithful stand-in. A verify script drives `up` and `sync` and asserts the properties that matter:

```text
== CA delivered into the VM engine trust store at run time ==
  PASS: delivered CA present + valid at /etc/docker/certs.d/10.0.2.2:5601/ca.crt
== Write path is authenticated - an unauthenticated write is refused ==
  PASS: unauthenticated write refused with 401 (Basic write token required)
== Guest push over authenticated HTTPS SUCCEEDS ==
  PASS: guest push landed: manifest tag 'dev' present in the registry store
== No static CA baked into the avocado-vm overlay ==
  PASS: the overlay provisions the trust-store location only
  passed: 8   failed: 0
```

## What broke

- **The write listener spoke HTTP where the guest required HTTPS.** A QEMU guest reaches the host as `10.0.2.2`, which is not inside docker's loopback insecure exemption, so the guest - configured via the delivered `certs.d` CA - expects TLS. The listener was serving plain HTTP. The fix was to terminate the same per-project leaf TLS the other listeners already used, on the VM path only. On a real board this would have surfaced as a mysterious push failure.
- **A 2 MiB body limit rejected every real image layer.** With TLS fixed, the push reached the registry and died mid-stream with `HTTP 413 "Failed to buffer the request body: length limit exceeded"`. The embedded registry was buffering upload bodies under a framework default of 2 MiB; real layers are bigger. Lifting that cap on the write path (blobs stream to the on-disk store) fixed it. A trivial busybox image had slipped under the limit and hidden the bug - only a 5 MiB layer surfaced it.
- **A false-green almost slipped through.** `sync` only signals the running session; the push happens asynchronously. An early version of the check asserted the command's exit code and passed even when no bytes moved. The real assertion waits for the manifest to actually land in the registry store.

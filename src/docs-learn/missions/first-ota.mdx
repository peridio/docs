In this mission you go from zero to a verified over-the-air (OTA) update. You create a project from the heartbeat reference, connect it to Avocado Connect, and boot it on a QEMU virtual device. Then you add a new metric to the heartbeat script, publish it as a new runtime, deploy it, and watch the new field appear in the device's logs. The update merges live, with no reboot.

The pipeline is the same one you would use for a production fleet. Only the device is virtual.

Along the way you'll see each step done multiple ways where multiple tools support it: uploading a runtime from the **Avocado CLI** or **Avocado Desktop**, and creating a deployment from the **CLI**, **Desktop**, or the **Avocado Connect** console.

## How an OTA works in Avocado

- A **runtime** is the versioned artifact you deploy. You build it locally, then upload and publish it to your Connect project.
- A **deployment** targets a published runtime at a **cohort** of devices (optionally filtered to specific devices or tags).
- Devices verify every update against TUF signatures before installing. How the update applies depends on what changed: extension-level changes (like the heartbeat script change in this mission) merge live with no reboot, while updates that carry a new OS image apply to A/B partitions and reboot into the new slot, with automatic rollback on boot failure. See the [update architecture](/avocado-os/security/update-architecture) overview and the [activation process](/developer-reference/avocadoctl/runtime-management/activation-process) for the exact rules.

## Prerequisites

- The [Avocado CLI](/developer-reference/avocado-cli/installation) installed, and optionally Avocado Desktop if you prefer a GUI for upload and deployment
- Docker running on your machine. The CLI builds inside a container.
- No hardware. The device in this mission is a QEMU virtual machine. To use a board instead, see [Getting Started](/learn/get-started) for provisioning it, then follow the same steps.

## Step 1: Create the project

Create a project from the `shell-heartbeat` reference. Its `heartbeat` extension is a shell script, run as a systemd service, that logs system vitals as JSON every 30 seconds. That makes it a good first thing to update: you can see the change land in the device's logs.

```bash
avocado init --reference shell-heartbeat my-heartbeat
cd my-heartbeat
```

Run every command from here on inside `my-heartbeat`.

## Step 4: Build and boot your device

Install the dependencies, build the runtime, and provision a QEMU disk image:

```bash
# Install the SDK toolchain, extension dependencies, and runtime packages
avocado install

# Build the extensions and assemble the runtime
avocado build

# Create the bootable disk image for the dev runtime
avocado provision dev
```

Boot the virtual device:

```bash
avocado sdk run -iE vm dev
```

Log in as `root`. The `dev` runtime has no root password. Because the project was linked to Connect in Step 3, the device enrolls and claims itself into your project on first boot.

Confirm the device is online in Connect: open your project's fleet, find the device, and check that its status shows **Online**.

In the VM, watch the heartbeat output. Keep this terminal open: you'll see the update land here in Step 7.

```bash
journalctl -u heartbeat -f --no-pager
```

Each line is one JSON reading:

```json
{ "uptime": 42, "mem_free_kb": 398212, "mem_total_kb": 524288, "load_1m": "0.01", "ts": 1740700000 }
```

The numbers depend on your VM. Only the field names matter here.

## Step 5: Make a change and upload it

Add a new metric, free disk space, to the heartbeat script. In `heartbeat/overlay/usr/local/bin/heartbeat.sh`, read the free space on `/var` and add it to the JSON line. The root filesystem is a read-only image, so `/var`, the writable data partition, is the one that changes:

```sh title="heartbeat/overlay/usr/local/bin/heartbeat.sh"
#!/bin/sh
set -eu

# Source configuration
INTERVAL=30
[ -f /etc/heartbeat.conf ] && . /etc/heartbeat.conf

while true; do
  uptime_secs=$(awk '{print int($1)}' /proc/uptime)
  mem_free_kb=$(awk '/MemFree:/ {print $2}' /proc/meminfo)
  mem_total_kb=$(awk '/MemTotal:/ {print $2}' /proc/meminfo)
  load_1m=$(awk '{print $1}' /proc/loadavg)
  # highlight-next-line
  disk_free_kb=$(df -k /var | awk 'NR==2 {print $4}')
  ts=$(date +%s)

  # highlight-start
  printf '{"uptime":%d,"mem_free_kb":%d,"mem_total_kb":%d,"load_1m":"%s","disk_free_kb":%d,"ts":%d}\n' \
    "$uptime_secs" "$mem_free_kb" "$mem_total_kb" "$load_1m" "$disk_free_kb" "$ts"
  # highlight-end

  sleep "$INTERVAL"
done
```

Rebuild the runtime on your host. The heartbeat extension has no compile step, so this only repackages the overlay files:

```bash
avocado build
```

### On the device

Go back to the VM terminal that is following the heartbeat log. Once the device is **On target**, the heartbeat service restarts with the new script, and the next reading includes `disk_free_kb`:

```json
{
  "uptime": 542,
  "mem_free_kb": 397980,
  "mem_total_kb": 524288,
  "load_1m": "0.02",
  "disk_free_kb": 276480,
  "ts": 1740700500
}
```

To confirm which runtime is active, run `avocadoctl runtime list` in the VM. The newest runtime is marked active.

You shipped a change to a running device over the air, without a reboot.

## Rollback and safety

- What happens when a bad OS update ships? A/B rollback to the rescue — read our Field Note: [Two boots to trust an update](/field-notes/2026/06/20/two-boots-trust-update).
- For more information, see [Deployments](/avocado-connect/deployments) and the [update architecture](/avocado-os/security/update-architecture).
- Turning on a manifest-level security feature (`image.verity`, `var.encrypt`) over OTA has an ordering rule: an update is applied by the avocadoctl **already on the device**, so ship the current avocadoctl in a plain OS update first. [Security features](/developer-reference/security) covers which transitions work over OTA and which need a reprovision.
